3. App Setup & Team Management

Setup
Steps
  1. Go to Developer Dashboard — create a Team first (required)
  2. Create an App — provide name, at least one scope, and one redirect URI
  3. Copy your Client ID and Client Secret after creation

4. OAuth 2.0 Authentication

Auth

Key URLs

Authorization URL
api.prod.whoop.com/oauth/oauth2/auth
Token URL
api.prod.whoop.com/oauth/oauth2/token

Token Lifetime

Access Token~3600 sec (1 hr)
Refresh TokenWith offline scope
State parameterMin 8 characters
Steps — Get Access Token
  1. Send request to Authorization URL → user logs in with WHOOP credentials
  2. User grants consent to the requested scopes
  3. WHOOP redirects to your Redirect URL with an authorization code
  4. Exchange authorization code at the Token URL for an access + refresh token
  5. Pass the access token as Bearer in the Authorization header on all API requests
Steps — Refresh Token
  1. POST to the Token URL with grant_type: refresh_token, refresh token, Client ID, Client Secret, and scope: offline
  2. Use the new access token returned; old tokens are immediately invalidated
  3. Store the new refresh token for the next refresh cycle
Limits & Rules
Expired tokens return 401 Unauthorized
Must include offline scope to receive a refresh token
Concurrent refresh requests: only the  first succeeds ; subsequent ones fail
Revoke tokens via revokeUserOauthAccess when user disables integration
Recommended refresh interval: every  1 hour

5. Data Models

API Data

🔄 Cycle (Physiological Day)

Represents the user's biological day — not a calendar day
Fields: id, user_id, start, end (null if ongoing), timezone_offset, score_state, score
Score includes: strain, kilojoules, avg & max heart rate
Score states: SCORED PENDING_SCORE UNSCORABLE

😴 Sleep

Fields: id (UUID), cycle_id, user_id, start, end, nap (bool), score_state, score
Score includes: sleep stages, performance %, consistency %, efficiency %, respiratory rate
v1_id field will  not exist past 09/01/2025 

💚 Recovery

Fields: cycle_id, sleep_id (UUID), user_id, score_state, score
Score includes: recovery %, RHR, HRV, SpO2, skin temp (°C)
Only present when score_state is SCORED
Accessed via the Cycle endpoint in the v2 API

🏋️ Workout

Fields: id (UUID), user_id, start, end, sport_name, score_state, score
Score includes: strain, avg/max heart rate, kilojoules, distance, altitude, HR zone durations
100+ sport types supported (Running, Yoga, Gaming, Cooking, and more)
v1_id and sport_id will  not exist past 09/01/2025

Basic Profile

Body Measurements

6. Pagination

API
Steps
  1. Make a request to a collection endpoint (Cycle, Sleep, Recovery, Workout)
  2. Response includes a records array and a next_token string
  3. Pass next_token as a query parameter on the next request
  4. Repeat until next_token is empty — no more pages
  5. Use the limit query parameter to control how many records per page
Limits
Each endpoint has a  max allowed value  for limit (specified per endpoint in API docs)
Estimated data size: ~ 4 KB/day  per member (1 workout + 1 sleep + 1 recovery)
Each additional workout or nap adds ~ 1 KB

8. Webhooks

Events
Setup Steps
  1. Create an HTTPS endpoint that accepts POST requests and validates signatures
  2. Add the URL to your app's Webhook URL section in the Developer Dashboard
  3. Select model version: v2 (recommended, UUID) or v1 (legacy, integer)
  4. Save the app configuration
Event Types
workout.updated / workout.deleted
sleep.updated / sleep.deleted
recovery.updated / recovery.deleted
Create events are published as "updated" events
No webhooks for Day Strain, Cycles, or body measurements — use API directly
Signature Validation Steps
  1. Prepend the X-WHOOP-Signature-Timestamp header value to the raw request body
  2. Generate a SHA256 HMAC using your Client Secret as the key
  3. Base64-encode the result
  4. Compare to the X-WHOOP-Signature header — drop the request if they don't match
Limits & Rules
WHOOP retries failed deliveries  5 times over ~1 hour 
A unique endpoint is required  per app 
Webhooks are  notifications only  — you must call the API for actual data
Duplicate webhooks are possible — use trace_id to detect them
Webhooks can be missed — implement a reconciliation job as backup
Revoking a user's access token stops all webhooks for that user
v1 webhooks are  no longer published 
Best practice: return a 2XX status within 1 second and process events asynchronously via a queue to avoid delivery failures.

9. v1 → v2 Migration

Migration

Key Changes

Sleep & Workout IDslong → UUID
Recovery webhook ID (v2)cycle ID → sleep UUID
v1 API statusNo longer supported
New featuresv2 only

Endpoint Changes

/v1/activity/sleep
↓
/v2/activity/sleep
/v1/activity/workout
↓
/v2/activity/workout
Migration Steps
  1. Update all API endpoint calls from /v1/ to /v2/
  2. For existing stored v1 IDs, use GET /v1/activity-mapping/{activityV1Id} for a one-time ID lookup
  3. Update code to handle UUIDs instead of long integers for Sleep and Workout IDs
  4. Update webhook configuration to v2 model version in the Dashboard
  5. Update response handling for new Optional field patterns
  6. Test thoroughly with both v1 and v2 endpoints before switching production traffic
Limits & Warnings
The mapping endpoint (/v1/activity-mapping/) is for  migration only  — do not use in production
v1 webhooks are  no longer published 
Webhook model version must align with the API version you're calling
